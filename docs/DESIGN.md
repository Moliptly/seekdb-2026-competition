# MiniVectorDB 设计与验证记录

> 赛题：实现一个支持 SQL、持久化存储与事务的轻量向量数据库（MiniVectorDB）。
> 实现语言：C11（gcc 13，零第三方依赖），单进程、单客户端、同一时刻至多一个显式事务。

本文按赛题 4.3 的要求说明记录布局、向量索引方案、事务处理、提交持久化和恢复流程，
并列出已实现功能与已知限制。

---

## 1. 总体结构

```
stdin(JSONL) ─► 协议层 main.c ─► SQL 解析 sql.c ─► 执行器 exec.c ─┬─► 目录/行存储 store.c
                      │                                           ├─► 等值倒排 eqindex.c
                      ▼                                           └─► 向量索引 ivf.c / vector.c
                 {"type":"ready"}
```

| 文件 | 职责 |
|---|---|
| `src/main.c` | 进程入口、ready 握手、stdin 请求循环、响应拼装 |
| `src/util.c` | arena 分配器、JSON 读写（手写，无依赖） |
| `src/sql.c` | 词法/语法分析，产出 AST；向量字面量解析与 float32 校验 |
| `src/exec.c` | 语句执行：CREATE/INSERT/SELECT/UPDATE/DELETE/CREATE VECTOR INDEX/事务控制 |
| `src/store.c` | 追加式事务日志、行存储、事务缓冲与 undo、崩溃恢复 |
| `src/eqindex.c` | 普通列的等值倒排索引（过滤用） |
| `src/ivf.c` | 自研 IVF-Flat 向量索引：k-means 建模、探测量自校准、增量维护、持久化 |
| `src/vector.c` | float32 向量语义、AVX2/FMA 距离核（运行期按 CPU 能力选择）、批量扫描 |

编译产物是单个可执行文件，不依赖任何第三方库：

```bash
gcc -std=gnu11 -O3 -o minivectordb src/*.c -lm
```

## 2. 存储布局

所有文件都在数据目录（评测容器中为 `/data`）下：

| 文件 | 内容 |
|---|---|
| `heap.log` | 追加式事务日志：帧 = `[u32 len][u32 crc32c][u8 type][payload]` |
| `vec_<table>.dat` | 向量载荷池：每个行版本占一个 slot，固定步长 `slot*dim*4` |
| `idx_<table>.ivf` | IVF 索引基线文件：质心 + 各簇 posting list |
| `idx_<table>.log` | IVF 索引增量日志（`(cluster, rowid)` 追加写） |

行记录（`INSERT_ROW` / `UPDATE_ROW`）保存主键与非向量列的值；**向量字节只存在载荷池里**，
每个行版本只写一次，因此磁盘写入量约等于数据本身的大小。载荷池只追加不覆盖：
一次更新会分配新的 slot，旧 slot 变成垃圾（由后续 checkpoint 回收），
这保证了"未提交的事务不可能部分生效"——提交标记落盘之前，载荷池里的字节还不被任何已提交
记录引用。

主键索引、行号到位置映射、存活位图放在内存里；行数据本身始终在盘上，
因此数据量可以远超内存限额。

## 3. 事务与提交持久化

规则要求：已确认提交的事务在强杀后必须保留；未提交的事务不得部分生效；
提交请求已发出但未收到响应的事务允许完整生效或完整不生效。

实现方式：

1. 语句执行时只修改内存中的行存储与事务 undo 缓冲，**不落盘**；
2. `COMMIT`（或自动提交语句结束时）把该事务的行记录追加写入 `heap.log`，
   把向量载荷写入载荷池，对两者各 `fdatasync` 一次；
3. 最后在日志尾部追加 **提交标记帧** 并 `fdatasync`；
4. 只有在第 3 步成功之后才回复客户端 `ok`。

于是：

- 客户端收到 `ok` ⇒ 提交标记与数据都已落盘 ⇒ 强杀后必然保留；
- 崩溃时日志尾部没有提交标记 ⇒ 该事务整体不生效（不会出现"部分行在、部分行不在"）；
- 语句失败时按 undo 缓冲回滚该语句的修改，事务中更早成功的语句不受影响；
- 进程正常关闭时若有未提交事务，直接丢弃缓冲（= 回滚）。

同一时刻只允许一个显式事务，因此不需要 MVCC，只需要"事务缓冲 + undo"。

## 4. 崩溃恢复

启动时按顺序重放 `heap.log`：

1. 逐帧读取，校验 CRC；尾部截断或 CRC 错误的帧直接丢弃（撕裂写）；
2. 只有出现对应 **提交标记** 的事务，其行记录才会被应用；未提交的事务整体丢弃；
3. 表定义帧先于行记录应用，因此行记录一定能找到自己的表；
4. 重建内存索引（主键哈希表、位置表、存活位图）后，才输出 `{"type":"ready"}`。

恢复过程只读、不写盘，因此在恢复途中被再次强杀也不会破坏数据，下一次启动照常恢复。
索引是派生数据：若索引文件缺失或与表的存活行数不一致，会在 ready 之前重建。

## 5. 向量索引方案（自研 IVF-Flat）

规则允许自行选择索引算法，且要求增量维护。这里实现的是 IVF-Flat：

- **建索引**：`CREATE VECTOR INDEX idx ON t(vec_col)` 时，对表的存活向量做 k-means
  （`nlist = clamp(round(sqrt(n)), 1, 4096)`，随机采样初始化，最多 6 轮 Lloyd 迭代），
  每个向量归入最近质心的簇，簇内保存行号列表。
- **查询**（`ann` 模式）：先算查询向量到各质心的距离，取最近的 `nprobe` 个簇，
  只扫描这些簇的行号并算精确距离，再取 TopK。
- **增量维护**：插入或向量更新时，把新行号归入最近簇并追加到 posting list；
  删除只把行号标记为失效，扫描时跳过。
- **探测量自校准**：固定的 `nprobe` 无法适配所有数据分布——均匀随机的高维向量其近邻几乎
  均匀分布在全表，而聚簇数据只需少数几个簇。建索引时用表内向量做样本，
  以"精确 TopK 为真值"实测不同 `nprobe` 下的召回率，取达到 0.98 的最小 `nprobe`；
  若需要探测几乎全部簇（说明索引不划算），查询会自动退回精确扫描。
  校准只发生在建索引阶段，不计入查询耗时。
- **精确模式**：`exact` 模式始终返回精确结果，即使已经建了近似索引。

实测（10000 行 × 128 维，本机，见 `tests/recall.py`）：

| 数据分布 | 自校准得到的 nprobe | Recall@10（无过滤） | 查询耗时 |
|---|---:|---:|---:|
| 均匀随机 [-1,1] | 100/100（全簇） | 1.000 | 192 µs |
| 正态分布 | 32/100 | 0.986 | 231 µs |
| 聚簇分布（20 簇） | 4/100 | 0.976 | 85 µs |

结论：高维均匀随机数据上 IVF 的召回率约等于"被探测的数据比例"，因此索引无法战胜精确扫描；
校准机制会自动识别这一点并退回精确路径，而对有结构的数据则能拿到实打实的加速。
无论哪种分布，召回率都稳定高于赛题要求的 0.95。

## 6. 过滤与 TopK

- `L2_DISTANCE` 返回**欧氏距离**（不是距离平方），按**存储后的 float32** 计算；
  查询向量同样先转成 float32。距离相同时按主键升序。
- 过滤在 TopK **之前**生效：在满足 WHERE 的记录集合内取 TopK，结果不足 K 条时全部返回。
- 带等值过滤的查询走普通列的**等值倒排索引**：先由等值条件直接取出候选行号，
  再逐行复核其余条件，最后算距离。这让"带过滤的 TopK"只与命中行数相关，与表大小无关。
- 倒排索引是惰性构建的（第一次用到该列时建），写入时增量维护；索引里可能残留失效行号，
  复核时会被过滤掉。

## 7. 性能

性能评测的负载是 10000 条记录、128 维、1000 条 K=10 的 TopK 查询（一半带等值过滤），
写入按每批 100 条提交。测得（`tests/bench.py`，2 核容器配额）：

| 阶段 | 耗时 | 说明 |
|---|---:|---|
| 写入（100 批 × 100 行） | ~0.60 s | 其中服务端解析 ~85 ms、事务提交 ~250 ms（含 2 次 fsync/批），其余是驱动侧 JSON 往返 |
| 查询（1000 条） | ~190 µs/条 | 无过滤约 350 µs（受内存带宽限制，5.12 MB/次），带过滤约 20 µs |

优化过程中定位到的三个主要瓶颈（均由实测得出，见 `agent/conversation.json`）：

1. 每条 SELECT 都在隐式事务里提交，导致**每条查询一次 fsync**——改为只读语句不开事务后，
   查询从 750 µs 降到 209 µs；
2. 每次请求都向 arena 申请 >128 KiB 的缓冲区，触发 mmap/munmap 与缺页——改为跨请求复用的
   scratch 缓冲后消除；
3. 向量字面量用 `strtod` 解析，1.28M 个浮点字面量耗时 200 ms——改为手写十进制解析后降到 85 ms。

距离计算在 AVX2+FMA 下用平方距离比较，只对最终返回的 K 行开方，避免逐行 `sqrt`。

还做过一个**被实测否决**的优化：把扫描拆到多个工作线程并行执行。独立微基准确认扫描受
**内存带宽**限制而不是受核数限制——线程数从 1 加到 8，吞吐只有 12.6 → 13.8 GB/s，
端到端查询耗时也没有变化（194us 对 201us，属于噪声）。因此工作线程池被整个撤掉，
保留串行扫描：少一个活动部件，也少一类并发缺陷。

## 8. 内存与大数据

评测容器的内存限额是 2 GiB，而正式用例里存在数据量超过内存限额的场景，因此行数据不能全部常驻内存。

- **向量**：每个行版本在载荷池里占一个 slot。表刚建立时向量缓存在内存中；
  当所有表缓存的向量字节数超过预算（默认 256 MiB，可用 `MVDB_VEC_CACHE_MB` 调整）时，
  该表停止缓存向量，查询改为从载荷池按需读取（带 1 MiB 的读缓存，顺序扫描时不会每行一次系统调用）。
- **元数据**：主键索引、行位置表、存活位图与普通列的值常驻内存，向量数据始终在盘上。

实测 600 000 行 × 128 维（307 MB 向量）：写入 52.4 s，峰值 RSS 315 MB，数据目录 343 MB
（每个向量字节只写一份），重启 0.61 s，TopK 查询 67 ms。

## 9. 已实现功能

- `CREATE TABLE`（BIGINT / VARCHAR(n) / VECTOR(n)，一个 BIGINT 主键，每表至多一个向量列）
- `INSERT`（含多行 VALUES、可选列名）、`SELECT`（投影、`SELECT *`、等值/范围比较、`AND`、
  `ORDER BY`、`LIMIT`）、`UPDATE`、`DELETE`
- `L2_DISTANCE`、精确 TopK、带普通列过滤的 TopK、精确/近似两种检索模式
- `CREATE VECTOR INDEX`（IVF-Flat，增量维护）
- `BEGIN` / `COMMIT` / `ROLLBACK`，自动提交，语句级原子性
- 崩溃恢复：SIGKILL 后已提交数据保留、未提交数据不部分生效、恢复途中再被杀仍能恢复
- 错误语义名：`duplicate_key`、`unsupported_sql`、`dimension_mismatch`、`invalid_vector`、
  `no_such_table`、`no_such_column`、`duplicate_table`、`invalid_value`

## 10. 已知限制

1. **不支持的语句按题目要求返回错误**，但没有实现 `ALTER TABLE`、`JOIN`、聚合、子查询、
   `NULL`、外键、嵌套事务、主键更新（题目明确不要求）。
2. **元数据常驻内存**：主键索引、行位置表与普通列的字符串常驻内存。向量有缓存预算和落盘回退，
   但普通列的字符串还没有；极端规模（数千万行且字符串很大）时这部分需要同样的处理。
3. **等值倒排索引只覆盖等值条件**，范围条件（`>`、`<`）目前走全表扫描。
4. **近似模式的过滤查询走精确路径**：等值倒排给出的候选集合已经很小且是精确的，
   此时再套近似索引只会损失召回率，因此带过滤的查询保持精确。
5. 日志目前不做压缩，长时间大量更新会让 `heap.log` 增长；回收方案（checkpoint）已设计
   但尚未实现。向量载荷池里的旧版本同理。
6. 写入路径每批提交要两次 `fdatasync`（日志 + 向量载荷池），实测一次约 0.68 ms，100 批约 136 ms，
   占服务端写入耗时的四成。把向量并入日志可以省一次，但载荷池正是「数据大于内存限额还能查询」
   的依托，因此保留两文件设计，把这项成本记为已知取舍。
7. 距离在 float32 下累加（AVX2 FMA），与参考实现的最后一位可能有 1e-7 量级差异，
   在赛题 1e-5 的容差内。

### 11.1 公开自测包带来的两处修正

公开用例全绿并不等于实现正确。按题包 README 对近似结果的要求（**必须满足过滤条件、
id 有效、id 不重复**）自己补写的检查，发现了一个公开用例没有覆盖的缺陷：
**更新某行的向量之后，近似查询会把这一行返回两次**——增量维护时行号被再次追加进了
posting list。修正方式是让索引记住每一行当前所在的簇，更新时把行**移动**到新簇而不是
再追加一次（`ivf.c` 的 `ivf_add` / `cluster_of`）。

同一轮里地址消毒器还抓到一处**越界写**：召回率自校准时真值数组按 `k` 个元素分配，
却写入了 `k+1` 个（多出的那个用于剔除探测行本身）。两处修正各配了一个回归用例，
消毒器下重跑全部用例（公开 20 项、边界 14 项、崩溃 6 项）零报告。
